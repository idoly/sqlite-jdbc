# Architecture

## Dependency direction

```text
sqlite-driver -> sqlite-ffm -> JDK FFM
```

`sqlite-native` produces platform artifacts consumed at runtime by `sqlite-ffm`. Its public C ABI is the prefixed `sqlitejdbc_*` shim; amalgamation `sqlite3_*` symbols remain hidden to avoid process-level collisions. The driver contains a package-private handle-management layer, so no FFM or native-memory type appears in its public API.

## Java compatibility

JDK 25 is the minimum runtime. Every Java module compiles with `--release 25`; later JDK releases may run the Java 25 bytecode, while Java 17-24 are explicitly unsupported. The binding uses the standard `java.lang.foreign` API directly and has no third-party runtime dependencies.

Keeping FFM types behind `sqlite-ffm` is an architectural boundary rather than a bytecode compatibility mechanism: the driver's internal database layer owns SQLite semantics, while the FFM module owns native calls and memory conversion.

## Design

The implementation uses a small set of patterns tied to concrete responsibilities:

- `SQLiteConfig` is an immutable value object built through `SQLiteConfig.Builder`. Driver properties and `SQLiteDataSource` both use it, so defaults and validation have one owner.
- `NativeDatabase` is a facade over one sqlite3 handle. It serializes calls and owns every `NativeStatement`.
- `NativeStatement` is a resource owner around one sqlite3_stmt handle. It translates JDBC one-based indexes to SQLite zero-based column indexes.
- `ExecutionController` decorates statement operations with query timeout, native interruption, and exception mapping.
- `JdbcSupport` is the capability policy for result-set modes, generated keys, and unsupported-feature errors.
- `SqlExceptionMapper` maps SQLite primary result codes to JDBC exception categories and SQLStates.
- `SQLiteNativeProvider` uses the initialization-on-demand holder idiom for one process-wide, stateless FFM binding.
- `PreparedStatementAdapter`, `ResultSetAdapter`, and `DatabaseMetaDataAdapter` reject unsupported JDBC methods by default; concrete classes override only supported behavior.

The driver module exports only `SQLiteDriver`, `SQLiteDataSource`, `SQLiteConfig`, and `SQLiteTransactionMode`. Concrete connection, statement, result-set, metadata, native-owner, and policy classes remain package-private.

## Naming conventions

- Public JDBC entry points and concrete JDBC implementations use the `SQLite` prefix. Package-private native resource owners use `Native`, and raw binding types live in the `sqlite-ffm` package.
- JDBC overrides retain the parameter vocabulary used by the JDK interfaces, such as `columnIndex`, `columnLabel`, `parameterIndex`, `resultSetType`, and `autoGeneratedKeys`.
- FFM boundary parameters use full domain names: `database`, `statement`, `parameterIndex`, `columnIndex`, and `openFlags`. Abbreviations such as `db`, `stmt`, and unqualified `index` are not used there.
- Names include units when values are numeric durations, for example `busyTimeoutMillis` and `timeoutSeconds`.
- Resource-state preconditions use `ensure...`; argument checks use `validate...`; boolean-returning policy methods use predicate names.
- Generated Adapter parameters are named `unused1`, `unused2`, and so on because those implementations deliberately reject the operation without reading arguments.

## Ownership

`FfmSQLiteNative` performs raw native calls and temporary memory conversion. `NativeDatabase` owns the database handle and tracks every `NativeStatement`. A JDBC connection owns its JDBC statements, savepoints, transaction state, and result sets.

Text and BLOB binds use SQLite's transient-copy semantics. Column text and BLOB pointers are copied into Java values before the next `step`, `reset`, or `finalize` operation. Closing proceeds from result sets to statements to the database. Close failures are aggregated with suppressed exceptions rather than discarded.

## Concurrency and transactions

SQLite is compiled with `SQLITE_THREADSAFE=1` (serialized mode). The driver serializes operations on each native handle, and JDBC connection state changes are synchronized. Applications should still use one connection per concurrent unit of work instead of sharing a `Connection` across threads. SQLite permits concurrent readers but only one writer at a time.

JDBC manual-commit mode starts transactions lazily with `BEGIN DEFERRED`. `commit()` and `rollback()` close active cursors, complete the transaction, and leave manual-commit mode enabled; switching back to auto-commit commits an active transaction. Closing a connection closes all JDBC statements and rolls back any active transaction. Savepoints use driver-generated identifiers so user-provided names are never interpolated into SQL.

## Native distribution

Native artifacts use explicit platform identities:

```text
linux-x86_64-glibc
linux-aarch64-glibc
linux-x86_64-musl
linux-aarch64-musl
windows-x86_64
macos-x86_64
macos-aarch64
```

Linux builds run from base-image manifest digests in containers. Windows and macOS release artifacts are built and tested on native GitHub runners. Cross-compilation alone is not considered runtime verification.

Each platform is published as a `sqlite-native` classifier JAR containing:

```text
META-INF/native/<platform-id>/<mapped-library-name>
```

`NativeLibraryLoader` detects the current platform, hashes the resource, and extracts it under a versioned cache with a process-safe file lock. `sqlite.jdbc.library.path` bypasses classpath extraction, and `sqlite.jdbc.native.dir` changes the cache root.

## JDBC scope

The driver implements ordinary and prepared statements, forward-only read-only results, transactions/savepoints, generated row IDs, batch execution, timeouts/cancellation, LOB/XML values, and core database metadata. APIs with no SQLite equivalent (stored procedures, SQL arrays/structs, XA) report `SQLFeatureNotSupportedException` rather than pretending to succeed. See the [usage guide](USAGE.md) for the supported workflow and type mappings.
